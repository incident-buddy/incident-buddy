# 2026-03-22 インシデントチャンネルへのウェルカムメッセージ投稿 開発活動報告

## サマリー

- 完了した機能: インシデント宣言時に作成した専用チャンネルに、インシデント詳細（title / severity / description / 宣言者名）を自動投稿する
- 所要フェーズ数: Phase 1〜7（レトロなし、QA 1回 FAIL → 修正後 PASS）

## 技術的決定事項

### `buildChannelWelcomeMessage` を `buildIncidentMessage` と別関数にした

`buildIncidentMessage` は `#incidents` チャンネルへの通知用（チャンネルリンクの有無など通知特化）、`buildChannelWelcomeMessage` はインシデントチャンネル内の詳細掲示用で用途が異なる。混在させると両方の関心事が一関数に入り、変更時の影響範囲が広がる。

### ウェルカムメッセージを `if (!configPath) return` の前に配置した

ウェルカムメッセージはコンフィグの有無に依存しない「常に投稿される」仕様のため、コンフィグ依存コードブロックの外に置いた。これにより「コンフィグなしの環境でもウェルカムメッセージが届く」という仕様が実装の構造に表れている。

### `welcomeResult.ok` の明示チェックを追加した（QA 指摘対応）

当初は `await client.chat.postMessage(...)` の結果をチェックせず SDK の throw に依存していた。QA エージェントが `coding-rules.md` の「`ok: false` 明示チェック」ルール違反を指摘し、修正した。

**理由**: SDK が `ok: false` を throw しない実装に変わった場合のバグを防ぐ。また、エラーハンドリングの意図がコードから明確に読み取れる。

### 却下した代替案

- **ephemeral message**: ユーザーが手動でチャンネルに参加した際の通知として ephemeral を追加する案。`member_joined_channel` イベントのサブスクライブが必要で変更コストが高いためスコープアウト。

## エージェント・チーム運営の観察

### QA エージェントの振る舞い

- 1 回目の評価: `coding-rules.md` の `ok: false` 明示チェックルール違反を正確に指摘。「SDK の throw に依存する偽陽性テスト」として問題を説明した
- 2 回目の評価（修正後）: PASS。3 つの受け入れ条件すべてを確認し、コーディングルール準拠も確認

### フィードバックループの健全性

- notification-rules.test.ts と incident-channel.test.ts が `notifyCount >= N` という count ベースのパターンでウェルカムメッセージ追加により壊れた。このリグレッションにより「関心のあるチャンネル・テキストが登場するまで待つ」というより堅牢なパターンへリファクタリングするきっかけになった
- MSW + Vitest の E2E テスト環境が `chat.postMessage` の複数呼び出しタイミングを可視化し、テストの脆さを早期発見できた

## 学んだこと

### 技術的洞察

- count ベースの Promise resolve（`notifyCount >= N`）は実装変更に脆い。「自分が関心を持っているイベントが発生したら resolve」というアプローチ（Approach A）の方が、追加の API 呼び出しが増えても壊れない
- `ok: false` 明示チェックはコーディングルールとして形式化されているが、「SDK の動作に依存しない」という意図がある。テストが pass していても、ルール準拠を QA ゲートで確認する価値がある

### プロセス改善の示唆

- QA エージェントへの文脈提供として `coding-rules.md` の存在を明示したことで、ルール準拠チェックまで網羅できた
- スコープ判断（ephemeral message の除外）をユーザーとの対話で Phase 1 中に確定したことで、実装フェーズでの手戻りがなかった
