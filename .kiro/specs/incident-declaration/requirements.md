# インシデント宣言フロー 要件定義

---

## 導入

incident-buddy の中核機能は、Slack の `/inc` スラッシュコマンドから始まるインシデント宣言フローである。チームメンバーが Slack を離れることなく、インシデントのタイトル・重大度・対象サービス・説明を入力してインシデントを宣言できる。宣言されたインシデントは Firestore に永続化され、宣言チャンネルへの通知投稿・専用インシデント対応チャンネルの自動作成・設定ファイルに基づく通知ルール実行が行われる。

このフローは他の全機能（ロールアサイン・タイムライン記録・解決操作）の起点となるため、最初に仕様化すべき基盤機能と位置づける。

---

## 実装コンテキスト

**既存実装: あり（部分実装）**

- `api/src/domain/incident/incident.model.ts` — `Incident` ドメイン型・`CreateIncidentParams` が定義済み
- `api/src/domain/incident/incident.repository.ts` — `IncidentRepository` インターフェース定義済み
- `api/src/infrastructure/incident/incident.repository.ts` — Firestore `store` / `resolve` 実装済み
- `api/src/adapter/slack-handler.ts` — `/inc` コマンドのルーティング構造のみ実装済み。`create_incident` ビューハンドラは `throw new Error("not implemented")` のスタブ状態
- `api/src/lib/config/index.ts` — Markdown 設定ファイルのパーサー実装済み（テストあり）
- **未実装:** モーダル表示・モーダル送信処理・チャンネル通知・インシデントチャンネル作成・チャンネルトピック設定・通知ルール評価

---

## 要件

### 1. /inc コマンドによるモーダル表示

**目的:** チームメンバー として `/inc` コマンドを実行し、インシデント宣言モーダルを開くことで、必要情報を入力できるようにしたい。

#### 受け入れ条件

**1.1** `/inc` コマンドが送信されたとき、slack-handler はモーダル（view ID: `create_incident`）を該当ユーザーに対して表示しなければならない。

**1.2** モーダルが表示されるとき、slack-handler は設定ファイルに定義された severity ラベルの一覧を重大度選択肢として静的セレクトメニューに設定しなければならない。

**1.3** モーダルが表示されるとき、slack-handler は設定ファイルに定義されたサービスラベルの一覧をサービス選択肢として静的セレクトメニューに設定しなければならない。

**1.4** 設定ファイルに severity が定義されていない場合、slack-handler は `Critical` / `High` / `Medium` / `Low` のデフォルト severity 一覧をモーダルに設定しなければならない。

**1.5** モーダルの `title` フィールドは必須のプレーンテキスト入力でなければならない。

**1.6** モーダルの `title` フィールドは最大 255 文字までの入力を受け付けなければならない。

**1.7** モーダルの `severity` フィールドは必須の静的セレクトメニューでなければならない。

**1.8** モーダルの `service` フィールドは必須の静的セレクトメニューでなければならない。

**1.9** モーダルの `description` フィールドは任意の複数行テキスト入力でなければならない。

**1.10** `/inc` コマンドのテキストが `config` である場合、slack-handler は現在の設定内容を ephemeral メッセージで返さなければならない（config 表示の詳細は別 spec で管理する）。

**1.11** `/inc` コマンドのテキストが `list` である場合、slack-handler はオープン中のインシデント一覧を ephemeral メッセージで返さなければならない（list 表示の詳細は別 spec で管理する）。

---

### 2. インシデント宣言（モーダル送信）

**目的:** チームメンバー として モーダルにインシデント情報を入力して送信し、インシデントが作成・記録されることで、対応を開始できるようにしたい。

#### 受け入れ条件

**2.1** `create_incident` ビューが送信されたとき、slack-handler は Slack に対して即時 `ack()` を返さなければならない。

**2.2** `create_incident` ビューが送信されたとき、incidentService は以下のフィールドを持つ `Incident` ドキュメントを生成しなければならない:
- `id`: ULID（`common/id.ts` の生成関数を使用）
- `title`: モーダルの `title` 入力値
- `description`: モーダルの `description` 入力値（未入力の場合は空文字列）
- `severity`: モーダルの severity 選択値
- `serviceName`: モーダルのサービス選択値
- `status`: `"open"`
- `slackChannelId`: コマンドが実行されたチャンネル ID
- `createdBy`: コマンドを実行したユーザーの Slack ユーザー ID
- `createdByName`: コマンドを実行したユーザーの Slack 表示名
- `createdAt`: 現在の UTC 日時（`Date`）
- `updatedAt`: `createdAt` と同値
- `resolvedAt`: `null`
- `resolvedBy`: `null`
- `resolvedByName`: `null`
- `responders`: 空配列
- `teamIds`: 空配列
- `serviceIds`: 空配列

**2.3** `Incident` が生成されたとき、incidentRepository は該当ドキュメントを Firestore の `incidents` コレクションに保存しなければならない。

**2.4** incidentRepository がドキュメントを保存するとき、`Date` 型フィールドを Firestore `Timestamp` 型に変換しなければならない（`lib/firestore.ts` の `toTimestamps` を使用）。

---

### 3. 宣言チャンネルへの通知投稿

**目的:** チームメンバー として インシデント宣言後に宣言チャンネルにメッセージが投稿されることで、チーム全体がインシデント発生を即座に認識できるようにしたい。

#### 受け入れ条件

**3.1** インシデントが Firestore に保存されたとき、slack-handler は宣言チャンネル（`slackChannelId`）に通知メッセージを投稿しなければならない。

**3.2** 通知メッセージにはインシデントタイトル・重大度（severity ラベル）・対象サービス名・宣言者の表示名を含めなければならない。

**3.3** 通知メッセージが投稿されたとき、slack-handler は返却された `ts`（メッセージタイムスタンプ）を `Incident.slackMessageTs` として incidentRepository 経由で保存しなければならない。

---

### 4. インシデント対応チャンネルの自動作成

**目的:** チームメンバー として インシデント宣言時に専用チャンネルが自動作成されることで、対応チームの会話を独立した空間で管理できるようにしたい。

#### 受け入れ条件

**4.1** インシデントが作成されたとき、slack-handler は Slack API を呼び出して新規チャンネルを作成しなければならない。

**4.2** 作成するチャンネルの名前は `inc-{yyyy-MM-dd-HH-mm}` 形式でなければならない。

**4.3** インシデント対応チャンネルが作成されたとき、slack-handler は作成されたチャンネル ID を `Incident.incidentChannelId` として incidentRepository 経由で保存しなければならない。

**4.4** インシデント対応チャンネルが作成されたとき、slack-handler はそのチャンネルのトピックを `[{severity}] {title} - 対応中` 形式に設定しなければならない。

**4.5** インシデント対応チャンネルが作成されたとき、slack-handler はウェルカムメッセージをそのチャンネルに投稿しなければならない。

**4.6** ウェルカムメッセージには設定ファイルに定義された全ロールのアサインボタンを含めなければならない。

**4.7** ウェルカムメッセージが投稿されたとき、slack-handler は返却された `ts` を `Incident.welcomeMessageTs` として incidentRepository 経由で保存しなければならない。

---

### 5. 通知ルールに基づくメンション送信

**目的:** インシデント対応責任者 として 重大度・サービスに応じた担当者へ自動でメンションが送信されることで、通知漏れなく適切な担当者が対応を開始できるようにしたい。

#### 受け入れ条件

**5.1** インシデントが作成されたとき、incidentService は設定ファイルの `notificationRules` を評価し、`severity` 条件と `service` 条件の双方を満たすルールを全て抽出しなければならない。

**5.2** 通知ルールの `severity` 条件が `==` の場合、インシデントの severity ラベルが条件の `label` と完全一致するときのみ対象としなければならない。

**5.3** 通知ルールの `severity` 条件が `>=` の場合、設定ファイルの severity リスト上で対象ラベルのインデックスが条件ラベルのインデックス以下（より重大な位置）であるとき対象としなければならない。

**5.4** 通知ルールの `severity` 条件が `<=` の場合、設定ファイルの severity リスト上で対象ラベルのインデックスが条件ラベルのインデックス以上（より軽微な位置）であるとき対象としなければならない。

**5.5** 通知ルールに `service` 条件が定義されている場合、インシデントの `serviceName` が条件の値と完全一致するときのみ対象としなければならない。

**5.6** マッチした通知ルールが存在するとき、slack-handler はインシデント対応チャンネルにマッチルールの `mentions` を全て含むメッセージを送信しなければならない。

**5.7** マッチした通知ルールが存在しない場合、slack-handler はメンションメッセージを送信してはならない。

---

### 6. 宣言チャンネルのトピック設定

**目的:** チームメンバー として 宣言チャンネルのトピックがインシデント情報に自動更新されることで、チャンネルを開いた際にインシデントの状況を一目で把握できるようにしたい。

#### 受け入れ条件

**6.1** インシデントが作成されたとき、slack-handler は宣言チャンネルのトピックを `[{severity}] {title} - 対応中` に設定しなければならない。

**6.2** トピックの `{severity}` は `Incident.severity` のラベル文字列を使用しなければならない。

**6.3** トピックの `{title}` は `Incident.title` の値を使用しなければならない。

---

### 7. タイムライン記録

**目的:** チームメンバー として インシデント宣言時のイベントがタイムラインとして記録されることで、インシデントの経緯を後から参照できるようにしたい。

> **注記:** タイムラインイベントの永続化先（Firestore サブコレクション設計）は、タイムライン機能の詳細 spec で別途定義する。本 spec ではサービス層での記録責務のみを規定する。

#### 受け入れ条件

**7.1** インシデントが作成されたとき、incidentService は `type: "created"` のタイムラインイベントを記録しなければならない。

**7.2** `created` タイムラインイベントには宣言者の Slack ユーザー ID（`userId`）を含めなければならない。

**7.3** `created` タイムラインイベントには宣言日時（`createdAt`、`Date` 型）を含めなければならない。

---

### 8. エラーハンドリング

**目的:** チームメンバー として エラー発生時に Slack チャンネルに通知が届くことで、処理が失敗したことを即座に認識し次のアクションを取れるようにしたい。

#### 受け入れ条件

**8.1** Firestore への書き込み操作が失敗した場合、slack-handler は宣言チャンネルにエラーメッセージを投稿しなければならない。

**8.2** Slack API 呼び出し（チャンネル通知投稿・チャンネル作成・トピック設定・ウェルカムメッセージ投稿）が失敗した場合、slack-handler は宣言チャンネルにエラーメッセージを投稿しなければならない。

**8.3** `create_incident` ビューの送信処理中に予期しない例外が発生した場合、slack-handler は宣言チャンネルにエラーメッセージを投稿しなければならない。

**8.4** エラーメッセージを投稿するとき、slack-handler はエラーの `AppError.type` フィールドをメッセージテキストに含めなければならない。

**8.5** エラーメッセージを投稿するとき、slack-handler はエラーの詳細テキストをそのまま Slack に表示しなければならない（セルフホスト型のため難読化は行わない）。

---

### 9. 設定ファイルの読み込み

**目的:** システム管理者 として Markdown 設定ファイルによってインシデント設定をカスタマイズし、組織に適した重大度・サービス・通知ルール・ロールを定義できるようにしたい。

#### 受け入れ条件

**9.1** `INCIDENT_CONFIG_PATH` 環境変数が設定されている場合、slack-handler はアプリケーション起動時に指定パスの Markdown ファイルを `loadConfig` 関数で読み込まなければならない。

**9.2** 設定ファイルの読み込みに成功した場合、slack-handler は読み込んだ `IncidentConfig` をモーダル生成・通知ルール評価に使用しなければならない。

**9.3** `INCIDENT_CONFIG_PATH` 環境変数が未設定の場合、slack-handler は `Critical` / `High` / `Medium` / `Low` のデフォルト severity を使用しなければならない。

**9.4** 設定ファイルが存在しない場合、slack-handler はデフォルト severity（`Critical` / `High` / `Medium` / `Low`）を使用してモーダルを表示しなければならない。

**9.5** 設定ファイルのパースに失敗した場合、slack-handler はデフォルト severity（`Critical` / `High` / `Medium` / `Low`）を使用してモーダルを表示しなければならない。

---

## 要件間の依存関係

```
9（設定ファイル読み込み）
  └─ 1.2, 1.3 が severity/service 一覧に依存
  └─ 5（通知ルール評価）が notificationRules に依存
  └─ 4.6（ウェルカムメッセージ）が roles に依存

1（モーダル表示）
  └─ 9 の完了後に実行（設定値をモーダルに反映）

2（インシデント宣言）
  └─ 1（モーダル送信が前提）
  └─ 2.3, 2.4（Firestore 保存）

3（宣言チャンネル通知）  ← 2 の完了後に実行
4（インシデントチャンネル作成）  ← 2 の完了後に実行
  └─ 4.5〜4.7（ウェルカムメッセージ）← 4.1〜4.3 のチャンネル作成後
5（通知ルール評価）  ← 2 + 9 の完了後に実行
6（宣言チャンネルトピック設定）  ← 2 の完了後に実行
7（タイムライン記録）  ← 2 の完了後に実行
8（エラーハンドリング）  ← 2〜7 の各ステップで発生しうる
```
