# 2026-03-21 スラッシュコマンドエラー通知 開発活動報告

## サマリー

- **完了した機能**: `/inc` コマンドおよび `create_incident` モーダル送信ハンドラーで例外が発生した際、元のチャンネルにエラーメッセージを公開投稿する機能
- **所要フェーズ数**: レトロスペクティブ 0 回（E2E は一発 pass）、受け入れテスト 5 回（QA エージェントのフィードバックループで繰り返し）
- **最終テスト**: 59 件 ALL PASS

## 技術的決定事項

### 選択したアプローチとその理由

1. **`postError` ユーティリティ関数の切り出し** (`slack/handlers/post-error.ts`)
   - `commands.ts` と `actions.ts` の両方から共通利用するため
   - アーキテクチャルール上 `handlers/` 内のユーティリティは許容範囲内

2. **`@slack/web-api` を直接インポートしない**
   - `@slack/web-api` は直接依存でないため、構造型 (`SlackClient`) で型付け

3. **`/inc config` を try-catch の外に移動**
   - 仕様書の除外事項「`/inc config` は既存の ephemeral 表示で対応」と一致させるため
   - 実装がスコープと正確に対応するよう調整

4. **テストで `vi.spyOn` を使用（`vi.mock` は使わない）**
   - `vi.mock` はファイルレベルでモジュール全体を差し替えるが、`app` のシングルトンが先にロードされると期待どおり動作しないことが判明
   - `vi.spyOn(incidentService, "create")` はオブジェクトのメソッドを直接差し替えるため、シングルトンキャッシュの問題を回避できる

### 却下した代替案

- **Bolt の `app.error()` グローバルエラーハンドラー**: `channel_id` が取得できないため要件を満たせない
- **テストで `throw new Error()` をMSWから使う**: MSW がネットワークエラーとして処理し、Bolt WebClient の挙動が `ok: false` と異なるため、`console.error` が呼ばれなかった

## エージェント・チーム運営の観察

### 受け入れテストエージェントのフィードバックループ

受け入れテストエージェントが 5 回 FAIL を返した。各 FAIL ごとに有効な指摘と無効な指摘が混在していた:

**有効な指摘（対応済み）**:
- メッセージフォーマット全体の検証 (`toMatch` 追加)
- `channel_id` 欠落テストで実際にサービス例外が起きていなかった（`vi.spyOn` 追加で解決）
- `create_incident` にも「エラー投稿失敗でクラッシュしない」テストが必要

**無効な指摘（対応不要）**:
- 「Bolt の WebClient は `ok: false` で例外を投げない」→ 実際には `WebAPICallError` をスローする（Red フェーズのログで確認済み）

### フィードバックループの健全性

受け入れテストエージェントは「新しい観点」を毎回追加してくる傾向があった。最終的に仕様書の受け入れ条件はすべてカバーされたと判断し、Phase 6 へ進む判断をした。今後は受け入れテストエージェントに「前回指摘以外の新規 FAIL 理由を 1 回につき 1 件に限定する」などの制約を設けると効率的かもしれない。

## 学んだこと

### 技術的洞察

- **Vitest の `vi.mock` vs `vi.spyOn`**: `vi.mock` はモジュールレジストリを差し替えるが、シングルトンとして作成済みのオブジェクトには影響しない場合がある。`vi.spyOn` はオブジェクトのプロパティを直接変更するため、シングルトンが持つ参照に確実に影響する。
- **MSW の `throw` vs `ok: false`**: MSW ハンドラーで直接 `throw` すると HTTP 500 になり、Bolt の WebClient は `HTTPResponseError` を投げるが、テスト環境での挙動が不安定。`ok: false` を返す方が実際の Slack API エラーシナリオに近く、テストも安定する。
- **セルフホストツールではエラー詳細をそのまま表示**: 内部ツールであることを考慮し、`error.message` をサニタイズせずに表示する設計が適切。

### プロセス改善の示唆

- 受け入れテストエージェントへの指示に「技術的な動作確認は既存のテスト PASS を尊重する」旨を明記すると、理論的な FAIL を減らせる
